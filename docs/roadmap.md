# Покрокова дорожня карта розвитку (Evolutionary Roadmap)

Для мінімізації ризиків інтеграції та забезпечення стабільного, безболісного розвитку монорепозиторію, розробка розбита на 4 послідовні фази. Кожна фаза завершується отриманням повністю робочого та протестованого продукту (MVP/Increment).

## 1. Фази розвитку проєкту

### Фаза 1: Базовий Web2 LMS-каркас
*   **Опис:** Створення монорепозиторію, налаштування БД PostgreSQL та авторизації. Розробка класичної навчальної платформи (відображення курсів, прості тести, кабінет студента та адмінка). Без складних алгоритмів.
*   **Епіки (Jira Epics):** `SBC-EP-INF`, `SBC-EP-SH`, `SBC-EP-BK`, `SBC-EP-CF` (частково), `SBC-EP-AF` (частково)
*   **Результат:** Робоча Web2-платформа, де користувачі можуть реєструватися та проходити статичні тести.

### Phase 2: Адаптивне навчання (Adaptive BKT & Behavioral Analytics)
*   **Опис:** Інтеграція алгоритму Bayesian Knowledge Tracing з підтримкою динамічного коригування параметрів Slip та Guess на основі поведінки та алгоритму автоматичного планування навчального треку (Task Sequencing). База даних розширюється таблицями BKT-станів (`bkt_state`), логів телеметрії (`telemetry_logs`) та поведінкових профілів (`behavioral_profiles`). Фронтенд рендерить граф навичок та запускає збір клієнтської телеметрії.
*   **Епіки (Jira Epics):** `SBC-EP-BKT`, `SBC-EP-CF` (візуалізація графа знань та збір телеметрії)
*   **Результат:** Студент бачить свій адаптивний граф знань у реальному часі; навчальний трек динамічно налаштовується під учня, пропонуючи завдання оптимальної складності залежно від розрахованого рівня засвоєння матеріалу.

### Фаза 3: ШІ-оцінювання та фоновий аналіз телеметрії (LLM Judge, BullMQ & Behavioral Analytics)
*   **Опис:** Розширене автоматизоване оцінювання студентського коду за допомогою глибокого асинхронного пайплайну:
    1. **Асинхронні черги (BullMQ + Redis):** Перенесення виконання коду в Node.js VM context та розрахунку BKT у фонові воркери (`EvaluationProcessor`) для запобігання блокуванню основного HTTP-потоку NestJS API при великому навантаженні.
    2. **LLM-Judge (Gemini API Integration):** Гібридне оцінювання студентських рішень за допомогою Google Gemini API (модель `gemini-2.5-flash`), яке здійснює семантичний аналіз коду, підказує оптимальні патерни та генерує людиночитабельні підказки без розкриття готового розв'язку.
    3. **Коефіцієнт Довіри (Trust Coefficient) & Динамічний Slip/Guess:** Обчислення інтегрального коефіцієнта довіри $C_{\text{trust}}$ на основі аналізу клієнтської телеметрії (WPM, паузи, copy-paste ratio, індекс втоми). Якщо $C_{\text{trust}} < 0.5$ (виявлено аномальне списування чи генерацію зовні), параметри $P(S)$ та $P(G)$ у моделі BKT динамічно підвищуються для зниження штрафного або компенсаційного приросту ймовірності $P(L_t)$.
    4. **Модульна Телеметрія та Виявлення Пікових Аномалій (Per-Module Telemetry & Peak Anomaly):** Збереження параметрів $WPM_{\text{skill}}$, $CopyPaste_{\text{skill}}$, $Fatigue_{\text{skill}}$ у контексті кожного окремого вузла DAG з розрахунком курсової Медіани та підсвічуванням локальних сплесків списування.
    5. **WebSockets Пуш-сповіщення:** Зворотній зв'язок у реальному часі через `TelemetryGateway` для оновлення UI студента у `apps/student` без опитування (polling).
*   **Епіки (Jira Epics):** `SBC-EP-LLM`, `SBC-EP-BKT` (розширення)
*   **Результат:** Студент вирішує завдання в кодовому редакторі; система миттєво приймає рішення, асинхронно оцінює семантику через LLM, динамічно коригує вагові коефіцієнти BKT на основі самостійності виконання та транслює розширений фідбек у студентський кабінет.

### Фаза 4: Блокчейн-верифікація (Web3 Trust)
*   **Опис:** Додавання випуску SBT та dNFT. Web3-авторизація інтегрується як альтернативний метод входу. Смарт-контракти та релейєр запускаються як незалежна система, що реагує на події завершення навичок у БД.
*   **Епіки (Jira Epics):** `SBC-EP-W3`, `SBC-EP-CF` (Web3 auth), `SBC-EP-AF` (SBT recovery)
*   **Результат:** Можливість увійти через гаманець та отримати Soulbound-токен за опановану навичку без сплати газу.

## 2. Архітектура Веб-Додатків Монорепозиторію (`apps/`)

Для дотримання принципу чіткого розмежування відповідальності (Role-Based Micro-Frontends) веб-частину розділено на 5 спеціалізованих застосунків:

- **`apps/web` (Порт `3001`):** Публічний промо-сайт, презентація адаптивної BKT-платформи та авторизація.
- **`apps/student` (Порт `3002`):** Кабінет Студента (Monaco Code Editor, збір телеметрії, візуалізація Skill DAG Map).
- **`apps/teacher` (Порт `3003`):** Кабінет Викладача (BKT Heatmap аналітика студентів, виявлення копіювання, індекс втоми, анулювання BKT-стану).
- **`apps/admin` (Порт `3004`):** Адміністративна Панель & CMS (Конструктор графа знань Skill DAG Builder, управління курсами та задачами).
- **`apps/docs` (Порт `3005`):** Портал технічної та користувацької документації.
