### 1. 📝 Обов'язковий порядок оновлення документації (Mandatory Progress Logging)

1. **Оновлення Денного Прогресу:**
   - Додавати короткий підсумок виконаних задач у файл [`docs/daily_progress.md`](file:///d:/PROJECTS/MAGISTERS/SMART-BKT-CHAIN/docs/daily_progress.md).

2. **Оновлення Детального Технічного Журналу:**

3. **Компіляція JSON для порталу документації:**

### 2. 🧩 Покрокова розробка невеликими ітераціями (Micro-Step Execution)
- Всі задачі розбиваються на прозорі **мікро-кроки** (Micro-Steps).
- Після кожного мікро-кроку проводиться перевірка збірки (`npm run build:*`) або unit-тестів (`npm run test:*`).
- Кожен завершений мікро-крок фіксується окремим `git commit`.
- **Формат повідомлень коммітів (Jira Conventional Commits):**
  Усі комміти обов'язково оформлюються за стандартом:
  `[SBC-XXX][EP-YYY] <type>: <опис англійською мовою>`
  де:
  - `SBC-XXX` — номер завдання з реєстру `docs/tasks/registry.md`;
  - `[EP-YYY]` — короткий код епіку (`[EP-INF]`, `[EP-SH]`, `[EP-BK]`, `[EP-BKT]`, `[EP-LLM]`, `[EP-W3]`, `[EP-ST]`, `[EP-TC]`, `[EP-AD]`, `[EP-LD]`);
  - `<type>` — `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`.

### 4. 🧪 Обов'язкова скрізна перевірка E2E (Mandatory End-to-End Testing)

- Після розробки або зміни наскрізних сценаріїв (збір телеметрії, перехід за графом BKT, скидання стану) **ОБОВ'ЯЗКОВО** виконувати або створювати Playwright E2E автоматичні тести (`npm run test:e2e`).
- Жодна наскрізна функція не вважається повністю завершеною без підтвердження скрізного проходження E2E тесту у реальному Headless браузері.

### 6. ♻️ Принцип Перевикористання та Модульності (Reusability & DRY First)
- **Аудит існуючого коду перед розробкою:** Перед написанням будь-якої нової сутності, утиліти, віджета або математичного модуля обов'язково перевіряти наявну кодову базу. Якщо функціонал уже реалізовано (повністю або частково), ми **ЗОБОВ'ЯЗАНІ його перевикористати**, розширивши за необхідності через інтерфейси чи конфігурацію, а не дублювати.
- **Проєктування з прицілом на перевикористання:** Якщо створюється новий функціонал, логіка або UI-компонент, де є вірогідність повторного використання в інших місцях (у спільних пакетах `@sbc/ui`, доменних модулях `domain/*`, спільних сервісах або віджетах кабінетів Студента / Викладача / Адміна):
  - Він проєктується як чиста, модульна та конфігурована одиниця (чисті функції, чіткі DTO/інтерфейси, композиційні компоненти).
  - Уникати жорсткої прив'язки (hardcode) до конкретного контексту одного контролера чи одного екрана, якщо його можна параметризувати.

### 7. 📐 Архітектурний Стандарт Бокових Панелей: Панель як Контейнер, Вміст як Секції (Side Drawer Sections Standard)
В усіх кабінетах платформи (`apps/teacher`, `apps/student`, `apps/admin`) висувна бічна панель (Side Drawer / Sidebar) розглядається як **чистий структурний контейнер (Shell)**, а **100% вмісту всередині обов'язково структурується через уніфіковані акордеонні секції**.

1. **Архітектурна сутність: «Панель — Контейнер, Вміст — Секції»:**
   - **Заборонено:** розміщувати в тілі бокової панелі монолітні неструктуровані списки, «голі» таблиці чи розрізнені контролери поза контекстом секцій (наприклад, суцільний список завдань або налаштувань без секційного оформлення).
   - **Обов'язково:** будь-який тематичний блок інформації (черга перевірки, фільтри, список студентів, конфігурація, метрики, легенда графа) огортається у стандартну інтерактивну секцію.
   - **Перевикористання компонента:** для побудови секцій обов'язково імпортувати та використовувати спільний компонент `<DrawerSection>` з пакету `@sbc/ui` (`@sbc/ui/drawer` або `@sbc/ui`).

2. **Безрамковий чистий лейаут (Borderless Clean Design):**
   - **Заборонено:** огортати секції у важкі зовнішні картки з рамками (`border border-slate-800 rounded-2xl bg-slate-900/60 p-...`). Тло сайдбара має залишатися монолітним, темним, глибоким і чистим.
   - **Розділення секцій:** тільки через тонкі семантичні розділювачі (`border-t border-slate-800/80 pt-2.5 mt-2` або чисті відступи `flex flex-col gap-2`).

3. **Інтерактивні індикатори згортання `+` / `−`:**
   - Кожна секція повинна мати можливість згортатися/розгортатися для оптимізації вертикального простору екрана.
   - **Заборонено:** використовувати стрілки `ChevronDown` / `ChevronUp` у шапках секцій сайдбара.
   - **Обов'язково:** використовувати векторні компоненти `Plus` та `Minus` з бібліотеки `lucide-react`.
   - **Стилізація індикатора:**
     - Розмір: `w-4 h-4 stroke-[2.5]`.
     - Контейнер: `p-0.5 rounded text-slate-400 group-hover:text-white group-hover:bg-slate-800 transition-all flex items-center justify-center`.
     - Стан: при відкритій секції показується `<Minus ... />`, при згорнутій — `<Plus ... />`.

4. **Шапка секції (Section Header Button):**
   - Робиться як доступна кнопка на всю ширину: `w-full flex items-center justify-between text-left px-0.5 py-1 text-slate-400 hover:text-white transition-colors cursor-pointer group`.
   - Ліворуч: тематична іконка (`w-3.5 h-3.5`), заголовок секції малими великими літерами (`text-[11px] font-bold uppercase tracking-wider`) у фірмовому кольорі розділу (наприклад, `text-cyan-400`, `text-purple-400`) та акуратний цифровий бейдж кількості елементів (`px-1.5 py-0.2 rounded text-[9px] font-mono bg-.../10 text-... border border-.../20`).
   - Праворуч: індикатор `Plus` / `Minus`.

5. **Анімація та оптимізація скролу контенту:**
   - Вміст розгорнутої секції має клас плавної появи `animate-fadeIn`.
   - Довгі списки елементів обов'язково обмежуються динамічною висотою (наприклад, `max-h-[calc(100vh-360px)] overflow-y-auto pr-1`) з тонким охайним скролбаром, щоб не ламати вертикальний лейаут сайдбара.

### 8. 📚 Дворівневий Стандарт Документації: Загальносистемний та Доменний по Застосунках (Dual-Level Architecture Documentation Standard)
Оскільки платформа Smart-BKT-Chain є мультипортальною системою, де кожен веб-застосунок (`apps/*`) є самостійним потужним ресурсом зі своєю унікальною педагогічною, інженерною або управлінською роллю, документація **ЗОБОВ'ЯЗАНА** будуватися на двох чітко розмежованих рівнях:

1. **Рівень 1: Загальносистемна Документація Платформи (Platform-Wide Core):**
   - Розміщується у кореневому каталозі `docs/`:
     - [`docs/architecture_overview.md`](file:///docs/architecture_overview.md) (або `docs/tech_stack.source.md`): загальна гексагональна архітектура, блокчейн-шар, шина повідомлень, спільні DTO контракти `@sbc/types`.
     - [`docs/daily_progress.md`](file:///docs/daily_progress.md) та [`docs/detailed_implementation_log.md`](file:///docs/detailed_implementation_log.md): денний прогрес і наскрізний технічний журнал монорепозиторію.
     - [`docs/roadmap.md`](file:///docs/roadmap.md) та [`docs/project_management.md`](file:///docs/project_management.md): епіки, стратегічні віхи та задачі.

2. **Рівень 2: Доменна Документація Застосунків (App-Specific Documentation):**
   - Усі застосунки платформи **ЗОБОВ'ЯЗАНІ** мати окремі вичерпні файли специфікацій у папці [`docs/apps/`](file:///docs/apps/):
     - [`docs/apps/study_portal.md`](file:///docs/apps/study_portal.md) (`apps/study`, порт 3006): дидактична місія (10–11 класи), навчальна програма курсу, UI Shell, специфікація **Режиму Зручного Читання (Zen Focus Reading Engine)**, пісочниця `CodePlayground`, картки оман `Misconceptions`.
     - [`docs/apps/student_portal.md`](file:///docs/apps/student_portal.md) (`apps/student`, порт 3002): інтерактивний тренажер, інтеграція Monaco Editor, поведінкова телеметрія (WPM, паузи, copy-paste), Сократівські підказки, калібрування BKT ($P(L_n)$).
     - [`docs/apps/teacher_dashboard.md`](file:///docs/apps/teacher_dashboard.md) (`apps/teacher`, порт 3003): кабінет викладача, когортна аналітика, виявлення аномалій академічної доброчесності, черга ручної перевірки робіт `ReviewQueueInspector`, візуалізація графу навичок курсу.
     - [`docs/apps/admin_portal.md`](file:///docs/apps/admin_portal.md) (`apps/admin`, порт 3004): методичний центр, налаштування та редагування графу навичок (Skill DAG), матриця складності BKT.
     - [`docs/apps/api_backend.md`](file:///docs/apps/api_backend.md) (`apps/api`, порт 3000): ядро бекенду на NestJS, BKT-секвенсор, WebSockets телеметрії, LLM Judge та збереження станів у БД.

3. **Обов'язкова автоматична компіляція у JSON:**
   - Кожен новостворений або оновлений документ із `docs/apps/*.md` **обов'язково** додається до процедури компілятора [`scripts/compile_docs.py`](file:///scripts/compile_docs.py), транслюється у структурований JSON у `docs/apps/*.json` та `apps/docs/src/data/apps_*.json` для публікації на порталі документації `apps/docs`.
